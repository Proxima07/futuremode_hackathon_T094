# 05 · 技術決策紀錄

記錄**為什麼**這樣設計。想推翻某個決定之前，先看這裡。

---

## D1 · 用版型，不讓 AI 自由生成座標

**決定：** 座標來自預先設計好的版型，AI 只做「挑版型 + 指派物件」。

**為什麼：**

| | 自由生成座標 | 版型 + 指派 |
| --- | --- | --- |
| 框會不會亂跳 | 會（每次算的結果不同） | 不會 |
| 構圖正不正確 | 看模型心情 | 一定對，是設計好的 |
| 模型輸出量 | 一堆浮點數 | 幾個 id |
| 延遲 | 高 | 低 |
| AI 掛掉怎麼辦 | 沒得救 | 退回預設版型 |

最後一列是關鍵。**永遠有一個能用的預設版型。**

**推翻的條件：** 如果發現四個版型涵蓋不了實際場景，
先加版型，不要改回自由生成。

---

## D2 · 按速度分層，不按功能分層

**決定：** 快層（本機，100ms）回答「現在在哪」，
慢層（遠端，1.5s）回答「應該在哪」。

**曾經考慮過的方案：** 兩個模型，一個判斷光影角度，一個判斷擺位。

**為什麼放棄：** 這兩件事沒辦法分開判斷。
「這個杯子該拿走」和「這個杯子該移到哪」是同一個決策的兩面。
兩個模型看同一張圖各自下判斷，結果會打架，而且無法仲裁。

**真正的洞察：** 使用者搬東西的時候，「應該擺哪」是不變的，
變的只有「現在在哪」。所以慢層算一次可以用好幾秒。

---

## D3 · 規則先跑，AI 後修正

**決定：** 打開相機立刻用規則給框，AI 回來之後平滑修正。

**為什麼：**
- 使用者不用等，體驗立刻成立
- AI 失效時產品不死
- 「高放後、低放前」本來就是規則，不需要模型

**這是整個專案最重要的風險控管。** 它把「延遲」從生死問題
降級成「體驗好壞」的問題。

---

## D4 · 語音全部預錄，不即時生成

**決定：** 30 到 50 句固定提示語在開發時就產生成音檔。

**為什麼：**
- 即時 TTS 有 1 到 2 秒延遲，引導語晚兩秒就沒用了
- 省額度
- 斷網也能用

**例外：** 商品描述那種非固定的內容才即時生成。

**贊助商考量：** 即時生成那段用 ElevenLabs（Track 02 贊助商，
「有效運用贊助商技術」是評分項）。
預錄那段可用國網的 `BreezyVoice` 當離線備援。

---

## D5 · 座標一律用 0 到 1 的比例

**決定：** 所有框的座標都是相對於畫面的比例。

**為什麼：** 每支手機螢幕尺寸與長寬比都不同，用像素會亂掉。
Demo 時評審用自己的手機，這件事一定會遇到。

---

## D6 · 送給 VLM 的圖壓到長邊 512

**決定：** 不送原始解析度。

**為什麼：** 判斷「東西該擺哪」不需要高解析度。
高解析度會被切成更多影像區塊，token 暴增，延遲跟著上去。

**如果延遲還是太高：** 降到 384 是下一張牌。

---

## D7 · 模型輸出用列舉值，不用句子

**決定：** `light` / `angle` 這類欄位回傳 `too_high` 這種列舉，
前端再查表換成中文。

**為什麼：**
- 模型只吐幾個 token，延遲最低
- 文案集中在 `phrases.js`，改字不用動模型
- 可以直接對應到預錄語音檔

**人話解釋走另一條路徑**（`/api/advice`），不擋主流程。

---

## D8 · 後端一定要有 validate 層

**決定：** VLM 的回應在傳給前端之前，一律過四道檢查。

**為什麼：** 模型會給不存在的 id、重複指派、
同時指派又要求移除。這些壞資料會讓畫面出現框飛掉或物件消失，
而那是 Demo 最傷的時刻。

**任何一關不過，退回上一個有效計畫。** 不報錯，靜默降級。

---

## D9 · 主力模型選 gemma-4-26B-A4B-it

**決定：** 國網的 `gemma-4-26B-A4B-it` 當主力。

**為什麼：** 既有的 VLM 管線就在用它，知道它的行為、
知道 schema 怎麼寫、知道 token 瓶頸在哪。**零學習成本。**

**待驗證：** `Microsoft-Phi-4-multimodal-instruct` 可能快很多。
這個任務很簡單（看圖挑選項），不一定需要 26B。
如果 Phi-4 夠用，延遲可能從 2 秒掉到 0.5 秒。

**Provider 順序：** 國網 → GMI Cloud → OpenAI。
GMI 放第二不只是備援，也因為它是贊助商（評分項）。

---

## D10 · 場景限定在二手交易商品照

**決定：** 不做通用攝影助手。

**為什麼：**
- 「好看」是主觀的，「能賣掉」是客觀的
- 有明確付費方（賣家想賺錢）
- 市面上八個競品全部在做通用攝影教學，這是差異化

**已知競品：** Acamera、FrameMaster、Cue Camera、GudoCam、
Wise Camera、cameracoach、Pose AI、Superpose、AureaCam。

**它們共同的缺口：** 全部在教「怎麼拿相機」（構圖、角度、光線），
**沒有一個在講「東西該怎麼擺」。**

Pose AI 和 Superpose 有做「疊輪廓讓你對齊」，但對齊的是**人的姿勢**。
**沒有人把這個機制用在物件上。**

**這就是我們的一句話：**
> 別的 App 教你怎麼拍，我們告訴你東西該怎麼擺。

---

## D11 · 前端不用打包工具

**決定：** 純 HTML / CSS / JS，用瀏覽器原生 ES modules 拆檔案。
不用 Vite、不用 React、不需要 Node。

**為什麼：**

1. **一台伺服器就夠。** FastAPI 直接把 `web/` 掛成靜態網站，
   前後端同源。沒有 CORS 問題，Cloudflare Tunnel 只要開一條。
2. **搬到樹莓派變成複製貼上。** 沒有 build 步驟、沒有 `node_modules`，
   `rsync` 過去就能跑。在 Pi 上跑 `npm build` 又慢又容易出事。
3. **開發環境單純。** venv + requirements.txt，PyCharm 一個直譯器搞定。
4. **UI 複雜度不需要框架。** 一個相機畫面、一個疊層 canvas、
   一個按鈕、一個結果頁。React 是殺雞用牛刀。

**代價：**

- TF.js 這類第三方函式庫要用 `<script>` 標籤載入，掛在全域，
  沒辦法 `import`。只有兩個，可以接受。
- 沒有熱重載。改完按 F5，這個專案的規模下差別不大。

**注意事項：**

- 原生 ES modules 的 `import` **必須寫完整副檔名**：
  `import { x } from "./lib/geometry.js"`（不能省略 `.js`）
- `<script>` 標籤要加 `type="module"`
- 必須透過 HTTP 提供，直接用 `file://` 開啟會被 CORS 擋掉。
  FastAPI 已經處理這件事

**推翻的條件：** 如果 UI 複雜到出現多層狀態同步的問題再考慮。
以目前規劃的畫面數量，不會發生。

---

## D12 · 第三方函式庫存本機副本

**決定：** `scripts/fetch_vendor.py` 把 TF.js 和 COCO-SSD 下載到
`web/js/vendor/`，`index.html` 本機優先、CDN 備援。

**為什麼：** 600 人的會場 Wi-Fi 一定會塞。
如果 TF.js 從 CDN 載不下來，**整個產品連物件偵測都做不了**，
連保命的 `rule` 模式都救不了你。

**這是 Demo 保命的第二道防線**（第一道是 `rule` 模式）。

**注意：** COCO-SSD 的模型權重預設也是從網路抓的。
`fetch_vendor.py` 要一併處理，否則只抓函式庫沒有用。
