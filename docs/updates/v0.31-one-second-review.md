# SnapFit v0.31：每秒取樣，持續重新判斷

本包接續已確認的 v0.30，只包含本次修改／新增檔案，保持目錄結構。

## 更新方式

1. 備份現有專案，解壓到專案根目錄，合併並覆蓋同名檔案。
2. 重新啟動 Uvicorn／Python 後端，手機重新整理頁面。這次前端排程和後端 Prompt 都有更新。
3. 不需新增套件，也不用修改 `.env`。Console／除錯面板應顯示 `v0.31`。

## 為什麼 v0.30 有 log，畫面卻可能反應慢

- 構圖迴圈會等模型回覆，再額外等 700ms。若推論耗時 1.8 秒，兩次請求就會相隔至少約 2.5 秒。
- 光線分析排在構圖前面，還會佔用下一輪；光線分析失敗也會拖長原本共用的重試間隔。
- READY 後改為 12 秒才做一次語意複查。本機的畫面變化偵測也和網路等待共用迴圈。
- 移動方向沒有改變時，前端會一直保留同一段 advice，忽略「再靠近一點」之類的新提示。

這些是程式中確認的延遲來源；未取得使用者當時的完整 log，不能據此確認每次延遲都來自同一原因。

## v0.31 改動

- **本機約每秒取樣一次**：即使模型還在推論，也持續檢查目前預覽畫面；分頁在背景時暫停。
- **構圖以每秒一次為目標**：從請求開始時計時，SEARCHING、GUIDING、READY 都適用。
  回覆完成後不再固定加 700ms。單次推論較慢時，完成後接續最新畫面，同時最多一筆遠端請求。
- **不累積舊照片**：不會把等待期間的每張影格排進佇列。送出時重新擷取當下畫面；
  若推論期間畫面已明顯改變，舊的 READY 或移動建議都會捨棄。
- **構圖優先**：光線分析優先利用剩餘空檔；持續忙碌約 30 秒後才安排一次補充更新，
  正在確認候選、可拍攝或新方向時繼續讓構圖先執行。READY 中仍暫停光線建議。
  光線失敗不再拖慢構圖重試。
- **固定目標，更新結論**：引導點、方向、版型、對準部位仍鎖定；新畫面持續重新判斷是否已到位。
  `GUIDING_SYSTEM` 明確要求先看本張是否已達完成標準，不能因上一輪是 move 就照抄舊動作。
- **同方向文字可以更新**：每兩秒最多更新一次剩餘動作說明。改方向仍需連續兩次確認，
  可拍攝仍需最近三次有效結果中的兩次確認，避免每秒檢查變成每秒改目標。
- **看得見判斷進度**：新增「判斷中／最近判斷幾秒前／暫無回應／畫面已改變」狀態。
  本機取樣不會假裝成模型已完成判斷；即使結論相同，最近判斷時間仍更新。

## 設定位置與速度邊界

`web/js/lib/config.js`：

```javascript
PLAN_INTERVAL_MS: 1000,  // 遠端構圖請求的目標起始間隔
SCAN_INTERVAL_MS: 1000,  // 本機取樣間隔
LIGHT_INTERVAL_MS: 6000,
LIGHT_MAX_DEFER_MS: 30000,
```

每秒取樣不等於模型保證每秒完成。網路、Gemma 推論、動態版型生成或光線分析超時，
仍可能拉長新結論的間隔。排程約每 50ms 檢查一次可用時機，不新增並行推論或補送佇列。
構圖請求失敗時保留 2／4／8 秒重試退避，本機仍每秒取樣，畫面會顯示正在重試。

這版 READY 也持續呼叫模型，因此該階段的呼叫量會高於 v0.30。
若要調整頻率，改上面兩個間隔即可；把間隔調得更小，並不能縮短單次模型推論時間。

## 驗證

通過 37 項 JavaScript 與 13 項 Python 離線測試、JavaScript 語法檢查及後端匯入檢查。
排程使用模擬時鐘與模擬 API，沒有呼叫使用者的 Gemma 端點或使用真實手機鏡頭。

- 模擬 400ms 推論：構圖請求於 0／1000／2000ms 開始，結果於 400／1400／2400ms 到達。
- 模擬 1800ms 推論：本機仍每秒取樣；上一請求完成後約一個排程刻度內送最新影格，不並行、不補送舊影格。
- READY 每秒複查，遠端忙碌時本機仍可偵測明顯畫面變化。
- 驗證光線優先序、慢光線回覆、重試、舊工作階段回應、切到背景及回到頁面的行為。
- 保留既有構圖鎖定、READY 投票、餐點與人像情境契約測試。

在專案根目錄可重跑（Node 24；Python 使用原專案環境）：

```bash
node --test tests/*.test.mjs
python -m unittest discover -s tests -p 'test_*.py'
```

手機更新後可以讓主體慢慢靠近固定點，再停住，觀察「最近判斷」持續更新，
以及兩次有效完成判斷後是否顯示可拍攝。模型仍可能誤判，這版沒有新增像素級物件追蹤。
